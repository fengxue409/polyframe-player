# P35 媒体库清理 + 任务清理

> 目标：媒体库与任务页都能「一次清掉一整批」——按视频多选、按规则一键选中；
> 执行前必须说清**删多少、腾出多少、删的是哪些**。

## 1. 起点：能删，但只能一条一条删

P33 之后，媒体库是「一部片一张卡」，任务页是一行一个任务。清理动作只有：

| 位置 | 已有能力 | 缺口 |
|---|---|---|
| 媒体库卡 | 单任务 hover「×」、展开后逐集「×」 | 一部 6 集的剧要删 6 次；没有「清已完成」这种批量意图 |
| 任务页 | 每行「清缓存」「删除」 | 缓存攒到几十个任务时，逐行点不现实 |
| 内核 | `task.delete` / `task.purge_cache` / `favorite.remove` | 批量调用要 N 次 RPC，每次都等 400ms 收尾 |

所以这次不是「加一个删除按钮」，而是把**选择**和**规则**这两层补上。

## 2. 为什么必须动内核：400ms × N

`TaskManager::delete_task` 的流程是「停 job → 等 400ms 让 worker 收尾 → 清缓存 → 删库行」。
前端循环调用 30 次 = **至少 12 秒**，而且这期间每删一条列表就重排一次，勾选的卡片会在手指底下换位。

新增两条批量接口，把等待**折叠成一次**：

```rust
// pf-engine
pub async fn delete_tasks(&Arc<Self>, ids: &[String]) -> (usize, u64, Vec<(String, String)>)
pub async fn purge_tasks(&self,        ids: &[String]) -> (usize, u64, Vec<(String, String)>)
```

实现要点：

1. `cleanup_targets()` 先把 id 分成「存在 / 不存在」并顺带判断**有没有正在下载的**；
2. 统一 `stop_download_job`，**只有确实在跑才等一次 400ms**（全是 ready 的任务直接跳过等待）；
3. 逐个 `purge_task_cache` → `delete_task_cascade` → `forget_task`（清 6 处内存态）；
4. 不存在的 id 进 `failed` 而不是整批报错 —— 清理场景里列表快照过期是常态。

单条接口改为委托批量（`delete_task` → `delete_tasks(&[id])`），避免两套逻辑漂移。

RPC（`pf-core`）：

| 方法 | 入参 | 返回 |
|---|---|---|
| `task.delete_many` | `taskIds: string[]` | `{ deleted, freedBytes, failed: [{id,error}] }` |
| `task.purge_cache_many` | `taskIds: string[]` | `{ purged, freedBytes, failed }` |
| `catalog.favorite.remove_many` | `ids: string[]` | `{ removed, failed }` |

`taskIds` 走新增的 `str_list_param()`：**空数组按参数非法处理**。批量删除收到空列表
通常是前端选中态错乱，静默返回成功会把这个 bug 藏起来。

## 3. 规则语义：三条容易写错的分界线

规则实现集中在 `lib/cleanup.ts`（纯函数，可单测）。

### 3.1 「已完成」≠ `status === 'ready'`

```
已完成 = 分片全下完（paused 在最后一帧也算）
      或 status ready 且确有过缓存
```

- **漏判**：边下边播看完停在 `paused`、但分片已齐的任务，只看 status 永远选不中，等于清理失效。
- **多判**：`ready` 但缓存已被清空的记录（「清缓存」会把状态打回 ready）不算已完成，
  它属于「空记录」。否则两条规则计数互相重叠，用户会看到「已完成 6 + 空记录 2」但总数只有 6。

### 3.2 「空记录」必须排除在途任务

刚创建的任务分片表还没建，`bytesDone = 0 / segDone = 0` 是正常的。
不排除 `pending/probing/downloading`，「清理空记录」会变成「新建即被清理」。

### 3.3 收藏规则：**没拉过片源 ≠ 没有片源**

`catalog.loadAllFavoriteSources()` 只填「已加载」的收藏键。规则里：

```ts
const list = sourcesByFav[f.id]
return Array.isArray(list) && list.length === 0   // 键不存在 → 跳过
```

把 `undefined` 当空数组，会误删用户刚收藏、片源快照还没拉回来的条目。
`cleanup.ts` 的回归里专门有一条断言锁住这个行为。

另两条收藏规则：

- **无剧集**：有片源但所有 `episodes` 为空（站方下架）。
- **同名重复**：名称归一（去空白/全角空格、小写）后分组，**保留 `createdAt` 最新的一条**。
  只做完全相等，不做模糊匹配 —— 与 P33 不做模糊标题聚类同理。

## 4. 交互：选择态 + 规则菜单 + 三问确认

### 4.1 选择态

- 媒体库下载 tab：卡片封面左上出现勾选框，点卡片任意位置也能选；「N 集」角标自动下移 28px 让位；
  收藏 tab 同理，「N 片源」标签下移。选择态里隐藏 hover「×」、播放键与多图角标，避免误触。
- 任务页：表格新增勾选列 + 表头全选，行点任意位置可切换；选中行整行染色。
- 选择态工具条：「全选 · 已选 N 部（M 集 · X MB） · 移除/取消收藏」，右侧「取消选择」。
- **换筛选 / 切 tab / 列表被清空 → 自动退出或清空选中**。否则会出现「已选 3 部」里 2 部看不见。

### 4.2 规则菜单（`CleanupMenu.vue`）

每一项都带「会选中多少条 + 能释放多少」：

```
清理已完成   2                      7.0 MB
已下完的任务，连缓存一起删；正在下载的不会被选中
清理失败     1                      300 KB
清理空记录   1
清空全部任务 6                      8.3 MB   ← 红色
```

点之前就知道影响面，而不是点完在确认框里才发现选多了。

### 4.3 确认框（`CleanupDialog.vue`）

清理不可撤销，确认框必须回答三个问题：

| 统计块 | 示例 |
|---|---|
| 删多少 | `2 部` / `6 个` |
| 影响范围 | `4 集` / `163 个`分片 |
| 腾出多少 | `8.3 MB` |

下面是名单预览（最多 6 条，其余折成「…等 N 项」），底部说明「收藏与播放历史不受影响」。
Esc / 点遮罩可取消，执行中按钮变「清理中…」并禁用。

## 5. 踩坑

1. **选择态里规则菜单是隐藏的**（`v-if="!selectMode"`），回归脚本第一版在选完直接去点 `.cm-trigger`，
   拿到 null 报错。不是 bug，是脚本顺序错了 —— 但顺手把「退出选择后恢复搜索框」加成了一条断言，
   防止以后改布局把工具条改没了。
2. **`.segmented button` 选择器不可靠**：改用「按钮文案包含『收藏』」定位 tab。
3. **`<script setup>` 不能有 ES 导出**：`CleanupMenuItem` 类型最初写在组件里，改用 `lib/cleanup.ts` 提供。
4. **`switchTab` 必须重置两个选择态**：否则从下载 tab 带着选中切到收藏，会让人以为选中的是收藏。
5. **`onDownloadRule` 不能复用「按组移除」的 builder**：规则的选中单位是任务（某几集），
   组的单位是整部片。先建组再覆盖 ids 会让「视频 N 部」和「集数 M」对不上。
6. **`removeFavorites` 不要调 `invalidateFavoriteSources()`**：它清空整张片源快照表，
   取消一次收藏会让下载墙的聚合与封面全部退回「一任务一卡」。只删被删的那几个键。

RPC 回归用 `LOCALAPPDATA=<临时目录>` 隔离，不碰真实收藏与缓存；真正的删除不是 mock：
建两个本地 HLS 任务 → 等 ready 且 `segDone >= 3` → `delete_many` → 校验 `freedBytes >= 3×2KB`
且 `task.list` 为空。

## 7. 未纳入本批

- **正在用 mpv 播的任务被批量删**时，原生子窗口的显隐仍沿用 `stop()` 的既有路径，
  没有额外 `mpvPushSurface(false)`。P26 的教训说明这里值得单独收口，但它属于播放链路，本批不动。
- 按体积排序 / 「只保留最近 N 部」的自动清理策略（内核 `cleanup.rs` 已有 TTL/LRU/容量三条，
  差的是把报告暴露到设置页）。
- 撤销（回收站）。清理走的是 `delete_task_cascade`，恢复需要额外的软删表。
