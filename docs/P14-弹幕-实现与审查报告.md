## 1. 为什么弹幕必须做两套渲染路径

这是整个设计里唯一"不能靠努力绕开"的硬约束，也是被误解最多的地方。

`pf-mpv/src/window.rs` 用 `CreateWindowExW(WS_CHILD, hWndParent = 主窗口 HWND)` 创建视频渲染表面。这个子 HWND **恒定绘制在父窗口客户区之上，不参与 Chromium 的合成器**。也就是说：在 libmpv 内核下，renderer 里的任何 DOM、任何 Canvas、任何 `position: fixed` 的层级调整，**都会被视频画面完全盖住**——这不是 z-index 问题，是两个不同的窗口系统层级。

`DESIGN.md` §3 原本计划的解法是"第二个透明 always-on-top BrowserWindow 覆盖层 + `setIgnoreMouseEvents({forward:true})`"。本次没有走这条路，因为代价明显更高（第二个窗口的生命周期、位置跟随、DPI、全屏切换、点击穿透区域、与主窗口的焦点同步），而 **libmpv 自带 libass**，把弹幕写成 ASS 字幕交给 `sub-add` 是最短路径。

最终形态是**双路径同源**：

| 内核 | 弹幕载体 | 代码位置 |
|---|---|---|
| hls / 原生 `<video>` | Canvas 2D 覆盖层（全功能） | `danmaku/engine.ts` + `components/DanmakuLayer.vue` |
| libmpv | ASS 字幕（libass 渲染） | `pf-danmaku/src/ass.rs` + `danmaku.ass` RPC + `mpv.command` |

两条路径**共用同一套轨道分配算法**（`track.ts` 与 `ass.rs` 保持同一语义），所以同一条弹幕在两种内核下的落位一致，不会出现"切内核弹幕乱跳"。

`DanmakuLayer` 在 mpv 模式下主动 `display: none`，注释里写清了这是 Win32 窗口模型的硬约束而非降级——否则后来的人会以为是 bug 去"修"。

**代价**：ASS 路径只能表达 libass 的样式能力（颜色 + 描边 + 定位 + 移动），做不了 HTML 那种发光、渐变、表情包、图片弹幕。真要这些效果，只能回到覆盖层窗口方案。

## 2. 链路与数据模型

### 2.1 RPC（15 个 + 1 个通用命令）

`pf-core/src/danmaku.rs`，全部 `danmaku.` 前缀：

```
settings.get / settings.set
credentials.set / credentials.clear / credentials.test
open / channels / channel.clear / channel.remove
match / fetch / list
send / ass / stats
```

外加 `mpv.command`——因为 `sub-add` / `secondary-sub-add` 是 mpv **命令**，`mpv.set` 根本改不了属性表里的对应项，必须新增一条能发任意命令的 RPC。

异常约定上有一处刻意设计：**发送被拒绝时不抛 JSON-RPC error，返回 `{ok:false, kind, message}`**。理由是被限流、内容为空、未绑定频道都属于"业务结果"而非"调用失败"，前端要按不同 `kind` 给不同文案，用 error 通道会被吞成一句"调用失败"。

### 2.2 存储

`pf-engine/src/danmaku_store.rs`：

```sql
CREATE TABLE danmaku(
  channel TEXT NOT NULL, id TEXT NOT NULL, time_ms INTEGER NOT NULL,
  text TEXT NOT NULL, mode TEXT NOT NULL DEFAULT 'scroll',
  color TEXT NOT NULL DEFAULT '#FFFFFF', source TEXT NOT NULL DEFAULT 'local',
  ctime INTEGER, PRIMARY KEY(channel, id),
  UNIQUE(channel, time_ms, text, mode)
);
CREATE TABLE danmaku_channels(...);
```

三个关键取舍：

- **时间存整数毫秒**。存浮点秒会让 `UNIQUE(channel,time_ms,text,mode)` 的去重失效（浮点相等几乎不成立），同一个 `p` 值解析两次就变两条。
- **`(channel, id)` 复合主键**。单 `id` 主键会让不同频道的相同 id 互相顶掉（弹弹play 的弹幕 id 只在单集内唯一）——这个 bug 是被 `channels_are_isolated` 单测抓出来的。
- **批量写入单事务**。8000 条一次 `insert_danmaku_batch`，逐条提交会把 6 小时的拉取窗口拖到分钟级。

### 2.3 弹弹play 接入

`pf-danmaku/src/dandanplay.rs`：

- 鉴权 `X-AppId` / `X-Timestamp`(unix 秒) / `X-Signature = Base64(SHA256(AppId + Timestamp + Path + AppSecret))`，其中 `Path` **不含 query**（这一条错了会 403，且报错信息完全看不出原因）。
- 剧集定位：`guess_episode_no()` 认「第N集 / EP12 / S01E03 / 裸数字」，`normalize_anime_title()` 去掉 `【】`、`（）`、`第N季`、年份后缀。这两个函数是匹配成功率的关键，也是 UTF-8 越界 panic 的高发区（§4）。
- 弹幕体：`p` 字段 `"时间,模式,颜色,用户ID"`，模式 1–3 滚动 / 4 底部 / 5 顶部，颜色十进制 RGB。
- 拉取结果 **6 小时 TTL 缓存**（`FETCH_TTL_SECS`），换集不重拉；`force:true` 可绕过。

凭据存 settings 表（`danmaku_app_id` / `danmaku_app_secret`），设置页有「保存并测试 / 仅测试 / 清除」三个动作，`credentials.test` 会真打一次搜索接口再回结果——不做假成功。

## 3. 三个关键算法

### 3.1 轨道分配（`track.ts` / `ass.rs` 同语义）

滚动弹幕按固定时长穿屏，速度 `v = (画布宽 + 文本宽) / duration`。两条同轨道可复用的**充要条件**：

1. 前一条尾部已完全进入屏幕：`v_prev × Δt ≥ w_prev + gap`
2. 前一条已远到新弹幕追不上：`v_prev × Δt ≥ w_new + gap`

条件 2 强于条件 1，但两条都校验能兜住"前一条特别短"的边界。顶部/底部固定弹幕走独立轨道池，按占用到期时间排队。

**屏满直接丢弃，绝不排队**。排队会让弹幕延后出现，越积越多，最后整屏全是"几秒前的弹幕"——这是弹幕产品的通行取舍，比丢几条更不可接受。

`track.ts` 导出了 `selfTest()`（7 组断言：同刻不重叠 / 隔久可复用 / 屏满丢弃 / 时间倒退保守拒绝 / 顶底互不干扰 / 超宽追尾保护 / 纵坐标边界），由 E2E 直接调用，不依赖测试框架。

### 3.2 时间轴缩放

库里**永远存弹幕源的原始时间轴**，缩放只发生在渲染侧（`scale_time` 线性贴合）。偏差 < 2% 视为同一版本，不缩放（避免无意义抖动）。

这样换片源、换剪辑版都不用重拉弹幕；同一个频道被多个片源复用时，各自按自己片长贴合。`scaleDanmakuTime()`（TS）与 `scale_time()`（Rust）保持同构，否则 ASS 路径和 Canvas 路径会错位。

### 3.3 双时钟统一（`clock.ts`）

- hls：直读 `video.currentTime`，每帧精确。
- mpv：`mpv.state` 事件 250 ms 一次，直接当帧时钟会**一跳一跳**。所以用「事件锚点 + `performance.now()` 墙钟插值」，每次状态事件重锚；单次外推上限 1.2 s，防止窗口挂起后时间跑飞。
- **seek 必须主动掰锚点**（`seekTo()`）：从发起 seek 到下一个 `mpv.state` 之间最多 250 ms，不掰的话弹幕会按旧时间轴继续跑，视觉上是"弹幕倒退"。
- `isDiscontinuity()`：倒退 > 0.35 s 或前进 > 1.5 s 判为 seek，触发 `hydrate()` 重建"此刻本应在屏"的弹幕——不做这一步，seek 到任意位置都会"先空屏再突然涌入"。

## 4. 审查发现的问题与修复

按严重度排序。**P14-1 / P14-2 是那种"日志看着全对、用户什么都看不到"的缺陷**，也是这次审查最有价值的部分。

| # | 严重度 | 问题 | 后果 | 修复 |
|---|---|---|---|---|
| P14-1 | 🔴 严重 | `pf-core` 的 `next_line_bounded()` 用裸 `read()` 绕过 `BufReader`，一次读到多行时**丢弃第一行之后的所有行** | 客户端把 `PF_AUTH` 首行和首个请求同包发出时请求永久丢失 → 表现为**随机超时**，且只有并发/首包场景复现。影响**所有 RPC 客户端**，不只弹幕 | 改 `read_until(b'\n')`，兼容 CRLF（与同时间窗的安全批次 M8「行读取限长」同源收敛） |
| P14-2 | 🔴 严重 | `DanmakuEngine.resize()` 在元素尚未布局时读到 0，照写把画布压成默认 `300×150`；而 CSS 尺寸（`width:100%`）之后不再"变化"，`ResizeObserver` 也不再回调 | 弹幕层挂载正常、开关正常、设置正常，**屏幕上一条弹幕都不显示**。连带 `tracks` 恒为 1、像素统计恒 0 | `resize()` 对退化尺寸早退并标记 pending；`start()` / 每帧 `syncSize()` / 低频 500 ms 兜底；`domVisible` 变可见时同步重量一次 |
| P14-3 | 🟠 中 | `recomputeCap()` 只会把 `adaptiveCap` 往下夹（`clamp(adaptiveCap, 8, base)`），不会回补 | 挂载早期 `tracks=0` 把上限压到 8 后**永远停在 8**（回补只发生在渲染循环里，暂停时循环不跑）→ 同屏最多 8 条、密度滑块形同虚设 | 布局/字号/密度变化时 `recomputeCap(reset=true)` 直接拉回基准；运行期仍按帧耗时逐步升降 |
| P14-4 | 🟠 中 | `send()` 把新弹幕插入时间轴后，若游标没越过插入点，下一帧区间消费会**再放一次** | 本地发送的弹幕在屏幕上出现两条一样的 | `if (idx <= this.cursor) this.cursor++`（`<=` 而不仅是 `<`）；E2E 加回归断言 |
| P14-5 | 🟠 中 | `make_id` 用 `{:.2}` 格式化时间参与哈希 | 12.345 与 12.35 生成同一 id → 不同弹幕被当重复丢弃 | 按毫秒整数 `(time*1000).round()` 参与哈希 |
| P14-6 | 🟠 中 | `normalize_anime_title()` 用 `replace_range(a..=b)`、`s[..idx]` 切多字节字符 | 标题含 `】`、`）` 或"第N集"时 **panic**（UTF-8 边界不在字符边界） | 一律按 `char.len_utf8()` 计算区间；`第N集` 回溯按 char 边界 |
| P14-7 | 🟡 轻 | `danmaku` 表用单列 `id TEXT PRIMARY KEY` | 不同频道的相同 id 互相顶掉，收藏多集后弹幕莫名变少 | 改 `PRIMARY KEY(channel, id)`（`channels_are_isolated` 单测覆盖） |
| P14-8 | 🟡 轻 | E2E 断言方式错误（不是产品缺陷） | 无头环境滚动弹幕停在"入场那一帧"（`x = 画布宽`，一个像素都还没进来），像素断言把"渲染正常"误判成"渲染失败" | 引擎加 `step(n)` 同步出帧；E2E 注入可推进的假时钟 |

另外两处**排查过程中的误判**，一并记录，避免后人重踩：

- 冒烟脚本一开始超时，看着像内核没响应，实际是脚本**只等 `PF_CORE_PORT` 不等 `PF_CORE_TOKEN`**——三条 `println!` 是独立写入，管道分包时 token 可能后到；后来必须两者到齐才算就绪。
- `proc.stdout.off('data')` 之后内核任何输出都会**卡住**（管道写满），必须保持持续消费。

## 5. 第三方弹幕源方案评估

### 5.1 为什么选弹弹play 作为主源

| 维度 | 弹弹play | B站 /  AcFun 官方 |
|---|---|---|
| 接口性质 | 有公开开放平台，`AppId/AppSecret` 签名，**接口形态稳定** | 无对外弹幕开放接口，只能逆向播放器接口 |
| 鉴权 | 静态签名，无需用户登录态 | 需要 Cookie / `buvid` / `w_rid` 签名，风控频繁变动 |
| 覆盖 | 以番剧为主，剧集/电影较弱 | 番剧最强，但**跨平台无法聚合** |
| 合规 | 官方申请、可署名 | 逆向接口 + 绕过风控，且违反 ToS |
| 失败模式 | 明确错误码，可分类降级 | 静默失败 / 412 风控页 |

结论：**弹弹play 是当前唯一"可以做成一等公民"的源**。选它不是因为最好用，而是因为它是唯一有稳定契约、能拿到明确错误、能合法申请的。

### 5.2 已实现的降级设计

- 无凭据 → `kind: no_credentials`，界面角标"仅显示本地弹幕"，不报错、不空屏。
- 无匹配 → `kind: no_match`，回带候选列表（`danmaku.match` 的 `candidates`）。
- 鉴权失败 / HTTP 5xx / 超时 → 分类文案，不是"解析失败"这种无信息量的话。
- `provider: 'local' | 'off'` 可整体关掉第三方源，只用本地弹幕。

### 5.3 风险与对策

| 风险 | 对策 |
|---|---|
| 接口非正式契约，可能改字段 | 解析层全部弹性处理（缺字段、类型漂移、`list` 为 null、坏条目），Rust 单测里有脏数据用例 |
| AppSecret 泄漏 | 只存本机 settings 表；不进日志（`log_startup_state` 只打"已配置/未配置"） |
| 单集弹幕量极大 | `MAX_BATCH_ITEMS` 均摊截断 + 单事务批量写；冒烟用 8000 条验证 |
| 源挂了 | 本地弹幕 + ASS/Canvas 双路径完全独立于第三方源 |

### 5.4 建议补的一块：本地弹幕文件导入

弹幕生态的事实标准是 **B站 XML**（`<d p="时间,模式,字号,颜色,时间戳,池,用户,行ID">文本</d>`）和 **ASS/JSON**。加一个「导入本地弹幕」入口（`danmaku.import`，拖入 xml/json → 解析成 `DanmakuItem` → 落 `source='local'`）成本很低，却能覆盖"弹弹play 没有这部片"的全部场景，也不必碰任何反爬。**建议作为 P14b 的第一项。**

### 5.5 明确不做的

不做 B站/AcFun 逆向弹幕接口。需要登录态 + 动态签名 + 绕过风控，稳定性差且违反 ToS；真要做只能做成用户侧浏览器扩展/本地代理，超出播放器职责。

## 6. 验证与复现

```bash
# 1) Rust 单测（全量 151 通过）
export PATH="/c/Users/<you>/.cargo/bin:$PATH"
cargo test --manifest-path apps/core/Cargo.toml
#   pf_core 4 / pf_danmaku 46 / pf_engine 44 / pf_parser 29(1 ignored)
#   pf_netdisk 11 / pf_magnet 9 / pf_proxy 7 / bt_local 1

# 2) 内核冒烟（无头，全本地假 origin，不依赖外网）82/82
pnpm core:build && node apps/core/scripts/smoke-p14.mjs

# 3) 真实窗口 E2E（读 canvas 像素作为渲染硬证据）28/28
pnpm -r build && node apps/core/scripts/e2e-p14.mjs
```

**冒烟 82 条**覆盖 9 组：A 设置夹取 / B 凭据与签名（用 node `crypto` **独立验算**签名，不复用被测代码）/ C 频道与缓存与 `force` / D 数据解析与脏数据 / E 发送限流去重 / F 清理与删除 / G ASS 生成 / H 异常 6 类 / I 并发（8000 条 + 20 并发拉取 + 20 并发发送）。

**E2E 28 条**覆盖：播放页 UI → 画布尺寸（含位图 ≥ CSS，专治 P14-2）→ 轨道自检 → 注入后**真的读到 canvas 像素**（32283 px）→ 500 条高密度（54718 px，单帧 0.57 ms）→ 字号变化轨道 19→10 → 发送即时上屏且不重复 → mpv 层隐藏 → ASS 生成 → 开关 → 设置页区块。

### 环境注记（重要）

本次 E2E 运行环境里 **`requestAnimationFrame` 完全不投递**（探测 3 帧超时 1500 ms 拿到 `frames: 0`）。原因是被遮挡/无头时 Chromium 会停掉帧生产，而 `ResizeObserver` 回调**跟着帧走**，所以它也不投递——这正是 P14-2 在本环境暴露得如此彻底的原因。

因此 E2E 全部改为「显式量尺寸 + `engine.step(n)` 同步出帧」，不依赖 rAF。**两种环境（有无帧）下结论一致**；有帧时 `tick` 与 `step` 走的是同一个 `frame()`。

## 9. 一条设计取舍的说明：为什么弹幕数据不放进 Pinia 的 reactive state

5000 条弹幕放进 `ref([])` 会被 Vue 深度代理，每次数组变更触发的是**数十万次 property trap**（`time`/`text`/`mode`/`color`/`source`/`id` × 5000），实测会让拉取完成的那一刻主线程卡住数百毫秒。

做法是：模块级裸数组 `rawItems` 存数据，store 里只放一个 `itemsVersion: number` 计数。组件 `watch(itemsVersion)` 后自己去裸数组里取——响应式只感知"变了"，不感知"变了什么"。渲染侧本来就是逐帧读裸数据，也不需要响应式。
