# P37 黑屏诊断与自愈

> 起因：用户连续两次报「视频播放不出来 / 还是黑屏」，且第二次发生在 P36 修复重建之后。

## 1. 结论先说

**在本机复现不出来。** 同一台机器、同一批片源、同一份用户数据，六条路径全部正常出画：

| 用例 | 数据根 | 结果 |
|---|---|---|
| `smoke-p21.mjs` 内核链路 | 临时 | 12/12 通过 |
| 冷启动 precache（`v.fengbao14.com` 981 片） | 临时（零缓存） | 首帧 6.2s，1920×1080 |
| 冷启动 stream | 临时（零缓存） | 首帧 9.1s |
| 持续播放 45s（precache + 4 worker 抢带宽） | 临时 | **1.00x 速率、缓冲 30s、0 卡顿** |
| 用户真实任务《嫁金钗 第1集》 | **用户真实库 + 缓存** | 首帧 1.8s，1920×1080 |
| 亮色皮肤 / 820×620 窄窗 / libmpv 内核 | 临时 | 均正常 |

其中「持续播放速率」是这次新加的判据：`ΔcurrentTime / Δ墙钟`。它能把「能出画但供不上码率」和「根本不出画」区分开 —— 前者表现也是黑屏转圈。实测 1.00x、缓冲稳定 30s，说明带宽不是瓶颈。

**结论：不是 P28/P30/P34/P36 引入的播放链路回归。**

## 2. 为什么之前查不动

失败现场只活在两个地方，而且都会消失：

1. 渲染层的调试抽屉（`player.logs`，内存里 100 条，关窗即失）；
2. 内核 stderr —— `rpc.ts` 里被**直接丢弃**：

```ts
// 修改前
this.proc.stderr!.setEncoding('utf8')
this.proc.stderr!.on('data', () => {})   // 注释：仅为调试日志，丢弃以防管道反压
```

而 `[pf-proxy] 回源失败 seq=…`、内核 panic、任务恢复失败**只**打在 stderr。等于最需要取证的那几行被系统性抹掉了。

第三个问题：错误提示只出现在播放卡下方的一行 `.alert` 里。卡片高度被预算锁死（P24/P25），布局紧时这行会被挤出视野 —— 用户看到的就是「一片黑、什么都没说」。

## 3. 本次改动

### 3.1 诊断日志落盘（`electron/main/diag.ts`，新增）

- 路径：`%LOCALAPPDATA%/PolyFrame/logs/app-YYYY-MM-DD.log`（8MB 上限，超出滚成 `.old`，只留一代）。
- 写入一律走 `fs.createWriteStream` **异步**，并带待写字节数上限（>2MB 直接丢弃）：Windows 下同步写管道会被内核反压卡死主进程，这是原来丢弃 stderr 的原因 —— 现在两全。
- 落盘内容：
  - `[core]` 内核 stdout/stderr 原文（含代理回源失败、任务恢复失败、libmpv 探测）；
  - `[core-status]` 内核状态机迁移（`idle → starting → online`）；
  - `[main]` 内核 spawn/exit；
  - `[web]` `did-fail-load` / `render-process-gone` / `unresponsive` / `preload-error`；
  - `[app]` `child-process-gone`（**GPU 进程崩溃 → 视频区全黑但进度条照走**，这类以前完全无痕）；
  - `[ui-*]` 渲染层转发的 warn/error、未捕获异常、未处理 Promise 拒绝；
  - `[ui-env]` 启动环境快照：视口、DPR、皮肤、内核、缓存档位、WebGL renderer。

  实测一行：
  ```
  [ui-env] viewport=1264x761 dpr=1 theme=light engine=hls cacheMode=precache
           gpu="ANGLE (Intel, Intel(R) HD Graphics 630 Direct3D11 vs_5_0 ps_5_0)"
  ```

- 噪音过滤：`ResizeObserver loop completed with undelivered notifications` 是 Chrome 已知良性告警，本应用大量用 RO 实测布局，每帧都可能刷一条，已在 `main.ts` 拦掉（否则真错误会被淹）。

### 3.2 失败必须在画面里说清楚

- `.video-wrap` 内新增 `.video-error` 卡片：标题「无法播放」+ 原因 + 「重新加载」+「复制诊断信息」。
  它挂在 `.force-dark` 作用域里，亮色皮肤下也是深底浅字。
- 「复制诊断信息」把现场压成 JSON：内核/皮肤/URL/任务 id/`readyState`/`networkState`/分辨率/`currentTime`/`buffered`/`video.error`/最近 20 条日志，同时写进日志文件。
- 占位图改为 `!playing && !playerError`，避免「占位文案 + 错误卡」叠在一起。
- 设置页「关于」新增「诊断日志」行：显示日志绝对路径 + 「打开日志目录」（`shell.showItemInFolder`）。

### 3.3 起播看门狗改两段式（自愈）

原来只有 15s 超时提示。现在：

- **9s 仍无帧** → 自动 `store.play()` 重载一次（重解析 playUrl / 重新拉分片 / 换链）。黑屏转圈最常见的成因（CDN 抖一下、代理 token 过期、首个分片被拦）大多能这样自己回来。
- **15s 仍无帧** → 置 `stuck`，给出原因与「重新加载」。
- 每轮起播只自动救一次（`autoRetried`，在 `playSeq` 变化时重置），失败源上不会无限重载。

## 4. 排查中顺带发现的两个环境事实

1. **`LOCALAPPDATA` 缺失时内核会静默回退到临时目录**（`pf-core` 的 `data_root()`）。
   这意味着从「剥了环境变量的启动器」拉起应用时，缓存/历史/片源全是新的 —— 表现是「每次都冷启动、缓存 0/N」，很容易被当成播放故障。
   内核启动日志第一行就会打 `data=…`，以后看这一行即可确认是不是同一份数据。
2. 用户库里 3 个任务都是 `precache`（会全量预下载）。本次实测证明**预缓存不会挤占播放**（代理回源是内联的，不排队等 worker，实测 1.00x），但冷启动首帧仍要 6–9s，取决于源站第一个分片的响应。

## 5. 复现脚本

- `.probe/probe8.mjs --mode precache|stream --wait 40`：隔离数据根（`LOCALAPPDATA` 指临时目录）冷启动首帧计时。
- `.probe/probe9.mjs --mode precache --dur 45`：持续播放健康度（速率/缓冲/卡顿），**判断「黑屏」到底是没出画还是供不上码率**。
- `.probe/probe3.mjs <url>` / `probe4.mjs --engine mpv --theme light --size 820x620`：单条路径起播。
- 想用真实数据根复现：spawn 时把 `env.LOCALAPPDATA` 指回 `C:/Users/<name>/AppData/Local`。
