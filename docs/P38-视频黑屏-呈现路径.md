# P38 · 视频「全屏能看、窗口黑屏」——呈现路径缺陷

> 用户反馈：**全屏时可以显示画面，不全屏时黑屏。**
> 这是 P28 引入视频区圆角之后的必然结果，与网络、解码、缓存、业务代码全部无关。

## 1. 结论先行

`.video-wrap` 上的 `border-radius` + `overflow: hidden` 是元凶。

- 有这两条 → Chromium 必须先把视频渲染到纹理、再做 mask 裁剪，然后才提交上屏。
- 在 **Intel 核显 + ANGLE/D3D11**（本机 `Intel HD Graphics 630`）环境下，这条「裁剪后提交」路径失败：**帧在合成器里是好的，但没有被送到屏幕上**。
- 全屏时 `<video>` 进入 **top layer**，绕过所有祖先裁剪，所以「全屏能看」。
- 去掉这两条后，视频直接以 overlay 平面呈现，立刻正常。

修复只有两行 CSS（`PlayerView.vue` 的 `.video-wrap`）：

```css
border-radius: 0;      /* 原 var(--r-md) */
overflow: visible;     /* 原 hidden */
```

## 2. 为什么前三轮（P36 / P37）都查不出来

这是本次最有价值的教训，必须记住：

| 取证方式 | 走哪条路径 | 能否发现本缺陷 |
|---|---|---|
| `page.screenshot()`（puppeteer） | Chromium 离屏合成 | ❌ 有画面 |
| `Page.startScreencast` | 合成器输出帧 | ❌ 有画面 |
| Electron `capturePage()` | 离屏合成 | ❌ 有画面 |
| `desktopCapturer`（DWM 桌面复制） | 真实上屏像素 | ✅ **纯黑** |

前三轮全部用前三种，它们**都绕过了「提交到屏幕」这一段**，所以永远显示正常。
只有 `desktopCapturer` 抓的是 DWM 真实桌面像素，才复现出问题。

实测同一时刻的对照数据（视频区 576×324）：

| 路径 | mean 亮度 | 暗像素占比 | 结论 |
|---|---|---|---|
| screencast（合成器） | 正常画面 | — | 有画面 |
| desktopCapturer（屏幕） | **9.61** | **96.0%** | 纯黑 |
| desktopCapturer + 去掉圆角 | **75.8** | **4.7%** | 有画面 |
| desktopCapturer + 修复构建 | **57.2** | **0.0%** | 有画面 |

## 3. 排除过的方向（都做过实验，均无效）

| 尝试 | 结果 |
|---|---|
| `--disable-direct-composition-video-overlays` | 无效，`mean` 仍然 9.61 |
| `--disable-gpu-compositing` | 渲染进程崩溃（detached frame） |
| `--disable-accelerated-video-decode` | 渲染进程崩溃 |
| `--use-angle=warp` | 白屏（`mean=241` 纯色） |
| `--disable-gpu` | ✅ 有效（`mean=103`），但代价是全应用软件渲染 |

`--disable-gpu` 有效这件事本身就是重要信号：它绕过整个 GPU 呈现路径，直接画到窗口。
但既然只去掉圆角就能解决，就不该牺牲全局硬件加速。

## 4. 判定流程（下次遇到「有声音/有进度无画面」先跑这个）

1. 用 `Page.startScreencast` 取一帧 → 看有没有画面。
   - **有画面** → 问题在「提交上屏」，是 GPU/合成问题，**不是**我们的业务代码。
   - **没画面** → 回头查解码、网络、分片。
2. 用 `.probe/grab.cjs`（`desktopCapturer`）抓真实屏幕同一区域，对比亮度。
3. 若 screencast 有、屏幕没有 → 逐个排查视频祖先链上的 `border-radius` / `overflow:hidden` / `clip-path` / `mask` / `backdrop-filter` / `filter`。

```bash
# 真实屏幕取证（需要窗口在前台且未被遮挡）
./apps/desktop/node_modules/electron/dist/electron.exe .probe/grab.cjs \
  '{"x":305,"y":168,"w":576,"h":324,"tag":"check"}'
# 输出 mean / pctDark / pctBright，并保存裁剪图
```

## 5. 为什么之前一直「复现不出来」

三轮排查的 probe 全部跑在**临时数据根**（bash 会话里 `LOCALAPPDATA` 为空，`pf-core` 回退到 temp），
加上截图走的是离屏路径 —— 等于换了一台机器 + 换了一种观测方式，两重失真。

后来把 `LOCALAPPDATA` 指回真实目录、并改用 `desktopCapturer` 之后，**一次就复现了**。

## 6. 顺带修正的认知

- `precache` 不抢播放带宽：代理分片是**内联回源**，不排队等 worker。P37 的怀疑可以撤销。
- 播放链路本身完全健康：45s 持续播放 1.00x 速率、30s 缓冲、0 卡顿。
- 内核 stderr 落盘（P37）没有白做 —— 它排除了源站、代理、解码这些方向，把范围收敛到呈现层。

## 7. 约束（写进代码注释了，别改回去）

**禁止给视频区（或任何包含 `<video>` 的容器）加 `border-radius` + `overflow: hidden`。**
需要圆角就让外层卡片提供，视频区保持直角。同理要回避 `clip-path`、`mask-image`、
给视频祖先加 `filter` / `backdrop-filter` / `mix-blend-mode`。

亮色主题下视频区是直角黑块，视觉上像一块嵌在卡片里的画框 —— 可接受，
比「能播但看不见」重要得多。
