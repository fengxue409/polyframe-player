# P39 首页多维筛选（类型 / 地区 / 年份 / 热度）

> 目标：把首页从「单维分类切换」改成「多维度筛选的影视库」，并明确筛选条件的**组合方式**与**交互方式**。
> 结果：四维单选、维度间取交集，热度支持豆瓣评分 / 站内评分 / 收录站数三种口径；筛选条件随时可见、可单条移除、可一键清空。

---

## 1. 先看清限制：能筛什么，数据里到底有没有

改之前必须回答一个问题：**地区、评分这些字段，采集站到底给不给？** 直接打了三个真实源站看字段分布（`ac=detail&pg=1`，每站 20 条）：

| 字段 | 非凡资源 | 暴风资源 | 极速资源 | 结论 |
|---|---|---|---|---|
| `vod_area` | 20/20 非空 | 20/20 | 20/20 | 有，但命名参差（`中国大陆`/`内地`/`大陆`/`美剧`…） |
| `vod_year` | 有 | 有 | 有 | 有，字符串 |
| `vod_douban_score` | 20/20 存在但**全是 `"0.0"`** | 3/20 有分 | 1/20 有分 | **稀疏**，且 `0.0` = 没打分，不是 0 分 |
| `vod_score`（站内） | 0/20 | 16/20 | 1/20 | 中等覆盖 |
| `vod_hits`（播放量） | 20/20 | 20/20 | 20/20 | 全有 |

由此定下两条产品决策：

1. **豆瓣评分只能当「加分项」，不能当唯一热度口径**。默认排序用「收录站数」（跨站聚合，永远有值），豆瓣评分是可选筛选。
2. **评分覆盖率必须告知用户**。否则用户选「豆瓣 9+」得到 0 条，会以为功能坏了 —— 实际是源站没给分。内核因此回传统计，UI 用黄条明说「本批 12 部中只有 7 部有豆瓣评分」。

## 2. 交互方式

### 2.1 布局

原来首页是「左竖排分类栏（频道 3 项 + 分区 5 项，占 148px）+ 右内容流」，一次只能表达一个维度，且「大陆」被塞进分区里当类型用，语义混乱。现在：

```
┌ 页头：影视库 · 2 个源站          [片库|收藏] [真实数据] [刷新] ┐
├ 搜索：搜片名，聚合全部源站，回车确认                    [搜索] ┤
├ 筛选  类型  全部 电影 剧集 动漫 综艺                    收起 ┤
│       地区  全部 大陆 香港 台湾 美国 韩国 日本 英国 泰国       │
│       年份  全部 2026 2025 2024 2023 2022 2021 更早           │
│       热度  不限 豆瓣9+ 豆瓣8+ 豆瓣7+ 站内8+ 3站以上           │
│       条件按「与」组合，行内单选（再点取消）；地区已含站方别名   │
├ 已选  地区：美国 ×   年份：2026 ×   清空全部                   ┤
├ 美国 · 2026 年  2 部        [热门|豆瓣评分|播放量|最新更新]     ┤
└ 卡片流                                                          ┘
```

- **左侧分类栏删掉**：148px 全给卡片区。频道语义并入「视图」（片库/收藏）与「排序」，不再有「热门/最新」既当频道又当排序的两套入口。
- **筛选与排序分家**：筛选改变命中集合，排序只改顺序。所以排序放结果栏右侧，不占筛选面板。
- **轮播只在「片库 + 无筛选 + 首屏够高（≥820px）」时出现**。筛选中它只会挤走结果；720p 下它会让片库一张卡都看不到。

### 2.2 组合方式（写进 UI，也写进代码注释）

| 规则 | 具体语义 |
|---|---|
| **维度之间「与」** | 类型 ∧ 地区 ∧ 年份 ∧ 热度，四条同时满足才显示 |
| **维度内部单选** | 每行只能选一个；**再点一次已选项 = 取消该维度**（回到「全部」） |
| **地区内部是「或」** | 仅限别名兼容：一个地区选项带多个站方写法（`大陆\|内地`、`美国\|美剧`），不是多选地区 |
| **「更早」是区间** | 不是某个具体年份，而是 `< 今年-5`（2026 年时即 ≤2020） |
| **热度是「指标 + 门槛」** | 豆瓣 9+/8+/7+、站内 8+ 看评分；「3 站以上」看收录站数（无评分也有数据） |
| **不组合搜索词之外的隐式条件** | 搜索词与四个维度同样取交集；搜索是先聚合再本地过滤同一套维度 |

「已选」行把当前生效条件列出来，每条可单独 ×，右侧「清空全部」一键复位。这解决的是最常见的一句抱怨：**「我不知道为什么列表是空的」**。

### 2.3 为什么不做多选

多选地区需要按地区循环请求再合并（服务端只有单值 `area` 过滤），代价是 N 倍回源，而收益很低 —— 「美国 + 韩国」这种组合的真实需求远小于「电影 + 2026 + 美国」。单选 + 可取消，交互成本最低且实现可预测。**如果将来要多选，正确做法是内核加 `areas: []` 并在 accumulate 期做 OR，而不是前端扇出。**

## 3. 数据层：为什么必须动内核

前端就算做了面板，卡片上没有 `area` / `score` 也没法展示和排序。所以这一批是「内核 + 前端」两层改动。

### 3.1 解析层（`pf-parser/cms.rs`）

`CmsVodItem` 新增三个字段，全部用已有的 `de_flex_id` 弹性解析（数字/字符串都接）：

```rust
vod_douban_score: String,  // "9.2" / 9.2 / "0.0"
vod_score: String,         // 站内评分
vod_hits: String,          // 播放量
```

新增四个纯函数（都带单测）：

| 函数 | 语义 |
|---|---|
| `parse_score(raw) -> Option<f64>` | 只认 `(0, 10]`；`"0.0"` / `"0"` / `"2534"`（有站把播放量填进评分位）一律 `None` |
| `parse_hits(raw) -> u64` | 纯数字才认，「1.2万」这种文案解析不出就归 0，**不猜单位** |
| `canon_area(raw) -> String` | 地区归一：`中国大陆/内地/大陆 → 大陆`、`美剧 → 美国`、`中国香港 → 香港`（顺序敏感，香港必须先于「中国」匹配） |
| `is_vague_area(raw)` | `其它/其他/未知/不详/""` 视为含糊值 |

### 3.2 聚合层（`pf-core/catalog.rs`）

同名同年合并时，各字段的合并规则不一样，必须逐条定：

| 字段 | 规则 | 理由 |
|---|---|---|
| `score` / `site_score` | **取最大** | 同一部片不同站打分不同，取最大代表「这部片最好的一面」，取平均会被低分站拖低 |
| `hits` | **求和** | 跨站播放量合计，量级差异大，只作热度参考（UI 上标注「仅作参考」） |
| `area` | 先到先得，但**含糊值让位**给后续具体值 | 有站填「其它」，后面的站填「美国」，应显示美国 |
| `source_count` | 条目数（原有） | 跨站热门度的主口径 |

同时把 `Filters` 提取成结构体（原来 `accumulate` 已经 3 个 `&str` 参数，加年份上限会变成 5 个）：

```rust
struct Filters { category, year, year_before: Option<u32>, area }
```

### 3.3 RPC 契约（`catalog.category`）

新增参数：

| 参数 | 类型 | 说明 |
|---|---|---|
| `yearBefore` | u32 | 年份上限（不含），用于「更早」；与 `year` 互斥 |
| `minScore` | f64 | 评分门槛，`0` = 不筛 |
| `scoreSource` | `"douban"` \| `"site"` | 用哪个评分字段 |
| `minSources` | u32 | 收录站数下限（「3 站以上」） |
| `sort` | `hot` \| `score` \| `hits` \| `time` | 新增 `score` / `hits` |

新增返回：

```json
"stats": { "total": 60, "doubanScored": 12, "siteScored": 30, "matched": 4, "filtered": true }
```

**`stats.total` 的语义要写清**：类型/地区/年份是在 `accumulate` 期过滤的，所以 `total` 是「这三个维度过滤后的候选数」；`minScore`/`minSources` 是聚合后过滤，所以它们不影响 `total`。两者无交集时 `total = 0` 是正确的，不是统计丢了 —— 这一点在回归里专门断言过。

### 3.4 一处顺手修掉的旧问题

```rust
// 改前：先 truncate(60) 再判 hasMore → len 恒等于 60，恒为 true
cards.truncate(60);
let has_more = cards.len() >= 20;
```
现在先算 `has_more` 再截断。行为不变（60 > 20），但不再是一句永远为真的废话。

## 4. 前端

### 4.1 纯逻辑先落地（`lib/catalog-filters.ts`）

把「选项定义 / 参数拼装 / 条件回显 / 覆盖率文案 / 客户端筛选排序」全做成纯函数，零 Vue 依赖 —— 这样 41 条判定规则能用 node 跑，不必为了测「再点一次是否取消」拉起整个应用。

### 4.2 服务端排序为什么必须回源

一开始我让 `pickSort` 只改本地状态、由 `sortCards` 重排已拿到的 60 条。回归立刻抓到问题：

> 内核是**先排序再截断 60 条**。客户端重排「按热门挑出来的 60 条」，等于「按评分排」只在这 60 条里排序 —— 和用户预期的「全站评分最高的 60 部」不是一回事。

所以排序改为回源请求（搜索态除外：搜索结果是已聚合的一页，没有服务端排序可发，本地重排即可）。

### 4.3 客户端判定与内核同源

搜索结果、收藏视图复用同一套 `matchesFilters` / `sortCards`，规则与内核对齐（类型关键词 `片`/`剧`/`动漫`/`综艺`，地区别名包含，评分 `≥` 且无分不算命中）。**收藏没有地区与评分字段，这两维在收藏视图直接隐藏**，而不是「留着但点了必然 0 条」。

**搜索 + 筛选是叠加的，但不再打一次全站**：搜索结果是已聚合的一页，改筛选只在这一页里重筛（回归里断言了 RPC 次数不增长）。此时内核不返回 `stats`，覆盖率文案就地在搜索页现算 —— 否则「搜完再选豆瓣 8+ 得到 0 条」没法解释。

## 5. 踩坑记录

| 坑 | 现象 | 处理 |
|---|---|---|
| 全局 `button { min-height: 34px }` | 筛选行 chip 被撑到 38px，四行面板 238px | `.fp-chips .chip { min-height:26px; height:26px }`，面板压到 206px |
| 新加的 `.segmented` 撞了旧回归选择器 | `.cleanupcheck` 用 `document.querySelectorAll('.segmented button')` 取「收藏」tab，命中的是首页隐藏的视图切换按钮 → 后续 8 条断言全崩 | 回归选择器加作用域 `.library-view .segmented button`；这也是提醒：**全局类名 + 无作用域选择器 = 定时炸弹** |
| 分组表头也是 `<tr>` | 「任务表行数」数出 11 而不是 6 | 断言改 `tbody tr:not(.grp-row)` |
| `stats.total` 在无交集时为 0 | 一开始以为统计丢了 | 是 `accumulate` 期过滤的正常结果，改注释 + 改断言 |
| 轮播把首屏吃光 | 720p 下页头+搜索+筛选面板已占大半，轮播再进来一张卡都看不到 | 轮播仅在 `innerHeight ≥ 820` 显示（内容优先于装饰） |
| 页头与结果区标题都是「影视库」 | 重复噪音 | 无筛选时结果标题改为「全部影片」 |
| mock 返回 `{}` 造出假 bug | 渲染层报 `Cannot read properties of undefined (reading 'length')` | 无头回归的假内核未实现的方法改为 reject（与「浏览器无内核」一致，store 本来就有 catch 分支） |
| mock 的 `stats` 与内核不一致 | 提示文案显示「12 部」而实际候选是 6 部 | 假内核也按「类型/地区/年份先过滤，再统计」实现，保持与内核同语义 |

## 7. 已知限制

1. **豆瓣评分覆盖率取决于源站**，可能长期偏低。UI 已明说覆盖率，但无法凭空造数据。想根治需要另接豆瓣 API（另开一批）。
2. **播放量是跨站求和**，不同站量级差异极大（有的站基数几万，有的几百万），只能作相对参考，UI 的 tooltip 已注明。
3. **地区只列 8 个常见地区**，没有「其他」选项 —— 「其他」需要「非空且不匹配任何已知关键词」的语义，得给内核加 `areaNot`，收益不大，暂不做。认不出的地区值会在卡片上原样显示（如「欧美」）。
4. **发现页仍有一套旧筛选 chip**（`store.catYear/catArea`），与首页各自独立、互不影响。两套筛选器并存属于历史遗留，下批可考虑让发现页复用 `catalog-filters` 的选项定义。
5. **单选而非多选**（理由见 §2.3）。
