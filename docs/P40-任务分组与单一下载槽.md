# P40 任务分组与单一下载槽

> 需求：任务列表按状态分类展示；非「播放中」的任务自动暂停；暂停后**不会自动恢复**，
> 必须用户手动点「启动」；状态切换与暂停/启动逻辑必须一致。
>
> 关键设计：**同一时刻只允许一个任务下载**（播放任务优先占槽）。分组不是纯展示，
> 它就是这套调度的规则表。

## 1. 分组判定（唯一真源 `lib/task-groups.ts`）

| 分组 | 判定 | 能做什么 |
|---|---|---|
| 播放中 | `status=downloading` 且 `id == playingTaskId` | 暂停 / 导出 / 清缓存 / 删除 |
| 下载中 | `status=downloading` 且不是播放任务 | 暂停 / 导出 / 清缓存 / 删除 |
| 准备中 | `pending` / `probing`（解析源站清单，未登记分片） | 删除 |
| 已暂停 | `paused`；或 `ready` 但分片没下完（job 已收尾）；或 `online` 之外的未完成态 | 启动 |
| 已完成 | 分片齐（`segDone >= segTotal`），或 `online` 档（本就不该有下载） | 播放 / 清缓存 |
| 失败 | `failed` | 启动（重试） |

判定顺序不能换：先看「内核 job 在跑」的 `downloading`，再看终态 `failed`，
再看 `pending/probing`，最后才按分片数区分「已完成 / 已暂停」。
若先判分片齐，一个刚建好、分片元数据还没登记的任务会被算成「已完成」。

`ready` 但没下完为什么归「已暂停」：内核在老实现里，job 一收尾就写 `ready`
（`finish_job`），所以**下了一半被停掉的任务在库里写的是 ready**。
分组必须按「能不能继续下」判断，不能照抄 status，否则这批任务既没有「启动」按钮、
又显示「已完成」，用户以为下载好了。

## 2. 下载槽策略（`stores/player.ts`）

只有一个槽：`downloadSlotId = playingTaskId || manualDownloadId`。

| 事件 | 行为 |
|---|---|
| 起播（`markPlayStart`） | `syncDownloadSlotForPlayback`：清空手动槽 → 若任务是 paused/failed 且非 online，先 `TaskResume` → `enforceSingleDownload(taskId)`，其余在下载的任务全部 `TaskPause` 并标「自动」 |
| 手动「启动」 | 播放中 → **直接报错**（不让它抢播放任务的分片，否则画面卡住）；否则占槽、收敛其余任务 |
| 用户「暂停」 | 让出槽，并清掉「自动」标记（这是用户按的，不是让位） |
| 停播 `stop()` | 槽清空 → `enforceSingleDownload('')` 把还在下的任务全停 → **此后不自动恢复** |
| 切缓存档 → 有预取 | 视为一次「我要下这部」：非播放中则占槽；播放中只登记意图并标记「自动」，等停播后手动启动 |
| 切缓存档 → online | 释放槽；`online` 没有预取可启动，行内不给「启动」 |
| 内核上线 / 状态变化 | `reconcileDownloads()` 刷新列表再收敛槽 |

**从设计上就没有「自动恢复」**：不记录「上次谁在跑」，重启、停播、切档都不会唤醒被暂停的任务。
系统只会**暂停**别人，永远不会**启动**别人。

## 3. 修掉的三个不一致（真机 CDP 抓到的）

### 3.1 `finish_job` 把 `paused` 覆盖成 `ready`

`pause_task` 只等 700ms（等最后一次进度心跳落地），但 worker 手上那批分片可能还要几秒才退出。
`finish_job` 晚到就无条件写 `ready`，于是：

- 徽章从「已暂停」变「未下完」
- 「自动」标记消失（旧判据要求 `status === 'paused'`）
- 用户看到「暂停了但状态没变」，以为按钮没生效

修复（`pf-engine/src/lib.rs::finish_job`）：收尾时先读内存状态，
**全量下完才写 ready，被停过就保持 paused**：

```rust
let all_done = total > 0 && done == total;
let paused = /* 内存里当前 status == Paused */;
let status = if failed > 0 && done == 0 { Failed }
             else if all_done { Ready }
             else if paused { Paused }
             else { Ready };
```

### 3.2 「启动」按钮在播放中直接消失

`canStartTask(t, group, playingTaskId)` 在有人播放时返回 false，按钮被 `v-if` 拔掉。
模板里其实已经写好了「禁用 + 说明原因」的分支，只是永远走不到。
临时不可用应该是**禁用**而不是隐藏 —— 隐藏等于告诉用户这个功能没了。

修复：`canStartTask` 只看「online 档 / 分组」，播放占用交给 `:disabled` + `title`
（`正在播放「X」，停播后才能启动其他下载`）。

### 3.3 `set_cache_mode` / `resume_task` 谎报 `Downloading`

老实现无条件 `emit(TaskStatus::Downloading)`，于是一个暂停中的任务改档位后，
库里写着「下载中」而实际没有 job 在跑 —— 进度条永远不动。
现在只有**真起了 job** 才写 `Downloading`，否则回显真实状态。

## 4. 界面

- 顶部一行 `.group-legend`：六个分组 + 各自数量（0 也列，避免「以为没有失败任务」）。
- 表格按组插入 `.grp-row` 表头：`分组名 + 数量徽章 + 判定规则`，跨满所有列。
- 行内徽章文案**跟随分组**（`statusTextOf`），不照抄 status。
- 被系统让位暂停的任务额外带一个「自动」小标（`title` 说明同一时刻只允许一个下载）。
- 空组不渲染表体，只在摘要里显示 0。

## 5. 验证（`.probe/probe40.mjs`，真机 Electron + CDP）

必须在隔离数据根跑（`LOCALAPPDATA=.probe/data40`），并且**走 `playTask()` 真起播** ——
只 `createTask` 不播放时 `playingTaskId` 为空，这套逻辑根本不会被触发（第一版探针就栽在这，
三条断言全落空）。

| 步骤 | 断言 | 结果 |
|---|---|---|
| 起播 A | 槽=A，A 在下载 | ✅ |
| 起播 B | 槽=B；A 变 `paused` 且进「自动」名单；在下载的只有 B | ✅ |
| 播放中看任务页 | 「启动」按钮存在、`disabled`、`title` 含「正在播放」 | ✅ |
| 播放中 `startTask(A)` | 被拒：`正在播放其他任务，播放结束后再启动该下载` | ✅ |
| 停播 +5s / +9s | 两个任务都 `paused`，**没有自动复活** | ✅ |
| 停播后 `startTask(A)` | 成功，槽=A，只有 A 在下载 | ✅ |
| 任务页 | 图例 6 项、分组行 2 条、徽章 `st-*` 与分组一致、「自动」标 1 个 | ✅ |

## 6. 已知边界

- 「自动暂停」标记只活在本次会话：`autoPausedIds` 不落库，重启后任务仍是 `paused`，
  但不再显示「自动」。这是故意的 —— 重启后谁都不记得当初为什么停的。
- 播放任务始终占槽：这意味着**看剧时不能同时预缓存另一部**，这是「单槽」的取舍。
  需要并发下载得改成按带宽/磁盘限额调度，不是放开槽位就完事。
