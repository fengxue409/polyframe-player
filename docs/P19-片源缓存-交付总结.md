# P19 片源内容缓存 — 交付总结

> 2026-10-28 · 范围：元数据 + 海报 + 播放直链；界面：设置页统计 + 列表角标
> 验证：Rust 单测 +7 / `smoke-p19`（见文末）/ typecheck + build + release 全绿

## 1. 缘起：先盘清「已经获取的东西到底留住了没有」

动手前把缓存链路整条读了一遍，按「已获取的数据」逐项对账：

| 数据 | 原实现 | 结论 |
|---|---|---|
| 播放分片 | `cache/{task}/{seq}.bin` + `segments` 表；三档模式、TTL/LRU/容量清理、`task.purge_cache` | **完备**，本批不动 |
| 网盘直链 | `LinkCache` 内存 512 条 + 60s 提前过期 + 401/403 强制换链 | 合理（直链本就短命，落盘反而有害） |
| 弹幕 / 磁力 / 解析接口清单 | 各自 SQLite 表 | 已持久化 |
| **采集站搜索 / 分类 / 详情** | 每次全量扇出，零缓存；失败即丢 | **缺口**：同词重搜、翻回上一页都要重打全部源站 |
| **海报 `/pic`** | 只带 `cache-control: 24h`，仍逐次回源透传 | **缺口**：列表滚动/重进发现页反复拉同一批图 |
| **TMDB 评分/人气** | 进程内 `HashMap`（24h） | **缺口**：内核一退，热门榜下次重打 30 次 |
| **P10 解析直链** | 每次点播都重新请求解析接口 | **缺口**：暂停后重进、连播重试反复解析 |

所以本批不是「加个缓存开关」，而是把**元数据类**的获取结果统一收口到一层可查询、可淘汰、可回退的持久缓存。

## 2. 设计

### 2.1 单表多 kind

```sql
CREATE TABLE src_cache(
  kind TEXT, key TEXT, body BLOB, bytes INTEGER,
  stored_at INTEGER, expires_at INTEGER, hits INTEGER, last_hit_at INTEGER,
  PRIMARY KEY(kind, key)
);
CREATE TABLE src_cache_stat(kind TEXT PRIMARY KEY, hits INTEGER, misses INTEGER, stale_served INTEGER);
```

- `kind` 是命名空间，同时承担统计与按类清理：`search | category | detail | tmdb | poster | parselink`
- `key` 由调用方定义，必须**自带源站维度**（`api|q`、`api|pg|hours`、`api|vodId`、`pageUrl|api`），
  这样删源站时能按 `api|` 前缀一次失效
- 命中率为什么单独一张表：**未命中时没有行可计数**，把 `misses` 挂在 `src_cache` 上永远为 0

### 2.2 TTL 只判新鲜度，不删数据

这是整层的地基语义：

- `expires_at > now` → **新鲜命中**，直接返回，零回源
- `expires_at <= now` → **旧值**，仍然可读；回源失败且策略允许时返回它（SWR）
- 真正删除只有两条路径：`prune`（过期超 7 天）与容量 LRU

「过期即删」会让离线回退彻底不可能 —— 用户断网时最需要的恰恰是那份过期数据。
反之若永不过期，`fromCache` 会冒充最新结果，所以**出参必须带 `stale` 标记**，界面要说清楚。

### 2.3 容量与维护

- 单条上限 4MB（`MAX_ENTRY_BYTES`）：异常大响应直接不入库，不报错
- LRU 按 `COALESCE(last_hit_at, stored_at)` 升序淘汰，删到 80% 水位；命中即续命
- 维护（prune + LRU）在 `remember()` 后触发，内部 15s 节流（`AtomicI64` 时间戳），调用方不必控频

### 2.4 读法统一在 `pf-core::srccache`

```rust
peek_fresh(store, kind, key)   // 只认新鲜
peek_stale(store, kind, key)   // 只认过期，并记一次 stale_served
remember(store, policy, kind, key, body)
fetch_text_cached(store, policy, kind, key, fut)  // fresh → 回源 → 回退
```

统一在这里的原因：**「源站挂了」不等于「没有数据」**，这个判断如果散落在各 RPC 里，
必然出现「搜索回退了、详情没回退」这类不一致。

## 3. 接入点

| 位置 | key | TTL 默认 | 细节 |
|---|---|---|---|
| `catalog.search` | `api\|q` | 10 min | `ac=detail` 优先、空则回退 `ac=videolist`；**空结果不写缓存**（否则一个空列表会被固化一整个 TTL） |
| `catalog.category` | `api\|pg\|hours` | 5 min | 大类/年份/地区是本地过滤，不进 key（同一个上游响应可服务多组筛选） |
| `catalog.detail` | `api\|vodId` | 30 min | 追更巡检走同一条，天然复用 |
| TMDB | `name\|year` | 24 h | 落盘替换原 `pop_cache`；**无命中仍不缓存**（片库会更新，下次该重试） |
| `/pic` 海报 | 图片 URL | 7 d | 命中回字节 + `x-pf-cache: hit`；图床挂了回退旧图；content-type 按**魔数**还原（不回存响应头） |
| `parse.resolve` | `pageUrl\|api` | 10 min | 只缓存直链；**不回退过期直链**（签名链过期会让播放器报误导性错误） |

失效策略：
- 删源站 → 按 `api|` 前缀清 `search/category/detail`
- 删解析接口 → 清空 `parselink`（key 的 api 在尾部无法前缀匹配，且总量与 TTL 都很小）
- 解析结果 JSON 化失败、缓存体解析不出来 → 视为脏缓存，当场失效重来

## 4. 并发模型的连带改动

采集站扇出原来是 `tokio::spawn`（要求 `'static`），而 `CacheStore` 只能借（`engine.store() -> &CacheStore`）。
三条扇出路径（搜索、分类、追更）统一改成**借用型 `join_all`**：

- 并发语义不变（HTTP 全在 await 点让出，一轮一批 12 路）
- 少了一层 `'static` 约束，也不必为了缓存去改 `CacheStore` 的持有方式
- 追更那里踩了一次 `E0505`：`batch.into_iter().zip(join_all(futs).await)` 里 `futs` 还借着 `batch`，
  必须先 `let done = join_all(futs).await;` 再 zip

## 5. 界面

- **设置页 › 片源内容缓存**：占用/条目、命中率（命中/未命中/降级复用次数）、按类分布表（逐类清理）、
  六档 TTL + 容量 + 回退开关 + 一键清空
- **发现页角标**（`cache-hint`）：
  - 有新鲜命中 → 淡蓝一行「3/18 个源站命中本地缓存（8 分钟前）」
  - 有回退 → 琥珀告警色「⚠ 2 个源站暂不可达，正在显示 2 小时前缓存的内容」
  - 全部真实回源 → 不占位（不制造噪声）
- **解析页**：命中直链时状态文案改为「命中直链缓存（未回源解析接口）」

## 6. 测试

### 6.1 Rust 单测（`pf-engine::srccache`，7 个）

fresh/expiry 语义、超限拒绝、命中与未命中计数、前缀失效 + 按类清空、LRU 续命与淘汰、prune 保留窗口、策略往返与越界夹取。

### 6.2 `smoke-p19.mjs`

用 `PF_SRC_CACHE_TTL_MS=2500` 把 TTL 压到 2.5s（默认按分钟计，冒烟里等不起），本地假源提供
CMS（`ac=list/detail/videolist`）、图床（真 JPEG 魔数）、解析接口（JSON 直链）：

- A 搜索：首次回源、二次 `fromCache=1` 且源站命中数不变
- B 详情：二次 `fromCache=1` 且零回源，剧集仍在
- C 海报：首次 `x-pf-cache: miss`、二次 `hit`、图床只被打一次、字节一致、content-type 正确
- D 直链：二次 `cached=true / via=cache`，解析接口只被打一次
- E 过期 + 源站 503 → 卡片仍在且 `stale=1`（详情同样回退）
- F 关闭 `offlineFallback` → 过期后不再回退，`failed=1`、卡片为空
- G 统计：entries/bytes/hits/misses/staleServed/按类分布齐全
- H 按类清空 → 再次搜索真实回源
- I 策略读写 + 越界夹取（`ttlSearchMin:1 → 2`、`capacityMb:0 → 8`）
- J 删源站 → 其名下搜索缓存归零

## 7. 踩坑与注意

1. **`PF_SRC_CACHE_TTL_MS` 是测试钩子，不是配置项**：它绕过所有 TTL 折算，只该出现在冒烟脚本环境里。
2. **空结果绝不写缓存**：采集站偶发超时返回空列表很常见，把空列表缓存 10 分钟等于「这个站坏了 10 分钟」。
3. **海报 content-type 靠魔数**：`src_cache.body` 是裸字节，没有地方存响应头；改回「存 JSON 包 content-type」会白付 base64 开销。
4. **直链不做 stale 回退**：这是本层唯一「宁可报错也不给旧值」的地方，签名链过期比没有更糟。
5. **`src_cache_lookup` 的过期命中不计 hit 也不计 miss**：只由 `note_stale` 记降级，
   否则命中率会被过期查询污染成一个没有意义的数字。
6. **MSVC 环境坑（本机）**：Git Bash 的 `usr/bin/link.exe` 是 GNU coreutils 的 `link`，
   会劫持 Rust 的链接步骤（报 `missing operand after '@...linker-arguments'`）；
   而只补 `PATH` 不补 `LIB/INCLUDE` 会依次报 `LNK1181: 无法打开 kernel32.lib` 与 `libsqlite3-sys` 构建失败。
   正确做法是三件套一起给：
   ```bash
   export PATH="/c/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/MSVC/14.36.32532/bin/Hostx64/x64:/c/Users/<you>/.cargo/bin:$PATH"
   export LIB='...\MSVC\14.36.32532\lib\x64;...\Windows Kits\10\Lib\10.0.22000.0\um\x64;...\um\ucrt\x64'
   export INCLUDE='...\MSVC\14.36.32532\include;...\Windows Kits\10\Include\10.0.22000.0\{ucrt,shared,um}'
   ```

## 8. 后续可做（未纳入本批）

- 缓存条目的**手动置顶/永不过期**（收藏夹里那几部片的详情值得长期留住）
- 按源站健康度联动 TTL（连续失败的站自动延长 TTL，减少无效回源）
- 跨设备同步（当前缓存是纯本机数据，不参与任何云侧同步）
