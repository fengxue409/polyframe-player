# P55 控制条：按钮与进度条合成一个组件

> 需求：把「选集 / 下一集 / 退出全屏」直接附加到进度条组件上，让两者在视觉和结构上
> 形成一个整体；并明确按钮相对进度条的定位方式、尺寸如何对齐、数值变化与按钮交互时
> 如何保持同步。

## 1. 为什么必须自研控制条

原生控制条是 Chromium 的 **closed shadow tree**：

- 不能往里塞按钮（`::-webkit-media-controls-*` 只能隐藏，不能插入）；
- 读不到它的轨道位置、悬停位置、拖动状态（`shadowRoot === null`）；
- 元素的 `getBoundingClientRect()` 只有整条控制条的框，拿不到轨道本身。

所以「按钮贴进度条」在原生控制条里**没有实现路径**。P55 的做法是全屏时把原生控制条
整体交出（`:controls="!isFullscreen"`），改用一条自研控制条接管播放/暂停、进度、静音、
选集、下一集、退出全屏。窗口模式仍用原生控制条，不受影响。

> 代价：全屏下没有任何原生控件兜底，所以点画面 = 播放/暂停、双击 = 退出全屏必须自己补
> （`onVideoClick` / `onVideoDblClick`），否则用户会觉得「点画面没反应」。

## 2. 定位方式：紧贴轨道末端，同处一行（兄弟节点）

三个候选方案，选的是第三种：

| 方案 | 结构 | 问题 |
|---|---|---|
| 嵌入轨道内部 | 按钮绝对定位在 `.fs-track` 里 | 吃掉轨道有效长度；轨道的 `pointerdown` 会抢走按钮的点击；窄屏时按钮压住游标 |
| 悬浮于轨道上方 | 按钮 `position:absolute; bottom:100%` | 浮层与条分离，视觉上是「两个东西」；hover/常态切换会有位移 |
| **紧贴末端、同一 flex 行** | 按钮是 `.fs-track` 的**兄弟节点** | 无 —— 见下 |

```
.fs-bar              （绝对定位，贴全屏底边，高 72px，纵向两行）
├── .fs-bar-head     片名 · 第 9/42 集 · 集名        （16px 文字行）
└── .fs-bar-row      一个 flex 行，align-items: center
    ├── button.fs-icon.play       30×30
    ├── .fs-time                  72px（mono + tabular-nums）
    ├── .fs-track       flex:1    命中区 30px，可视细条 5px
    ├── button.fs-icon.mute       30×42
    └── .fs-bar-acts              [选集 9/42][下一集 第10集][退出全屏]
```

关键点：**按钮与轨道是同一个 flex 容器的子项**，不是叠在轨道上的浮层。因此
「轨道末端 → 按钮起点」的距离就是容器的 `gap`（`--sp-3` = 12px），没有 magick number；
轨道用 `flex: 1` 吃掉剩余宽度，按钮 `flex: none` 钉在末端 —— 只有轨道伸缩，按钮不挪。

## 3. 尺寸与对齐：中线是算出来的，不是调出来的

| 元素 | 高度 | 说明 |
|---|---|---|
| `.fs-bar-row` | 30px | 行高由最高的子项决定 |
| `.fs-track`（命中区） | 30px | 可视细条只有 5px，居中在命中区内 |
| `.fs-rail`（细条） | 5px → hover/拖动 7px | `height` 变化不改变 30px 命中区，所以按钮不会被顶动 |
| `.fs-icon` / `.fs-act` | 30px | 与命中区同高 |
| `.fs-rail-knob`（游标） | 12px，`scale(.72)` → hover/拖动 `scale(1)` | `transform` 不参与布局 |

因为整行只有一个 `align-items: center`，`5px` 细条的中线与 `30px` 按钮的中线**必然重合**，
不需要 `top` / `margin` / `translateY` 去凑。实测（1920×1080）：

```
row.cy = track.cy = rail.cy = play.cy = 三个按钮的 cy = 1055
row.h = track.h = play.h = acts[i].h = 30
```

两个坑：

1. **全局 `button { min-height: 34px }`**。`height: 30px` 压不下来，必须显式写
   `min-height: 0`，否则按钮 34px、轨道 30px，中线虽对齐但上下沿参差。
2. **`--pf-fs-bar` 必须与脚本里的 `FS_BAR_H` 一致（72px）**。视频高度按它扣减、
   mpv 子窗口矩形也按它扣减；改一处不改另一处，全屏里的控制条会被画面盖住或留下黑边。
   同时 `.fs-bar` 的高度是**锁死**的：内容再多也不许变高，窄屏只减内容（隐藏标题、
   集名、`9/42` 角标），不换行。

## 4. 同步：一份数据源，零反向依赖

### 4.1 数值变化（进度在跑）

单一数据源：`playPos` / `playDur` 由两条内核分别喂（hls 走 `timeupdate`、mpv 走状态泵），
轨道填充宽度、游标位置、时间文本、`aria-valuenow` 全部从这两个 ref **派生**，
控制条侧不存第二份进度。所以不存在「按钮那边的读数和进度条不一致」。

布局上，按钮不可能被进度推走：

- 轨道 `flex: 1`，按钮 `flex: none`；
- 时间用 mono + `tabular-nums`，秒数变化字宽不变（实测 `00:08` 与 `00:19` 两态，
  `.fs-time` 都是 `l=62 w=72`）。

实测（同一次全屏会话，拖动使进度从 `00:08` 跳到 `00:19`）：

| 量 | 变化前 | 变化后 |
|---|---|---|
| 时间文本 | `00:08 / 00:30` | `00:19 / 00:30` |
| 已播填充宽 | 385px | **902px** |
| `.fs-track` | `l=146 w=1420` | `l=146 w=1420` |
| `.fs-time` | `l=62 w=72` | `l=62 w=72` |
| `.fs-icon.mute` | `l=1577 w=42` | `l=1577 w=42` |
| 三个按钮左沿 | `1631 / 1717 / 1826` | `1631 / 1717 / 1826` |

即：**只有填充宽度变了，一切都钉在原位**。

### 4.2 按钮交互

| 交互 | 轨道侧反应 | 按钮侧反应 |
|---|---|---|
| 悬停轨道 | 细条 5→7px、游标 `scale(.72)→1`、上方浮出时间气泡 | 无变化（不重排，`height`/`transform` 都不影响布局） |
| 按住拖动 | `.fs-track.scrubbing`：填充与游标跟手指走，`timeupdate` 不再把值拽回去；拖动期间**零 seek 请求** | 无变化；`setPointerCapture` 保证拖出轨道也继续跟手 |
| 松手 | `scrubbing` 解除，一次性 `commitSeek` 真正落盘 | 无变化 |
| 播放/暂停 | 轨道照常走 | 图标 `ico-play ↔ ico-pause` 切换（CSS 画的，不依赖字体） |
| 静音 | 无变化 | `.active` 高亮，状态写回 `<video>.muted`（mpv 走 `mpv.set mute`），原生控制条的静音也会通过 `volumechange` 反向同步 |
| 时长未知 | `.fs-track.idle`：降透明、`cursor: default`、`aria-disabled` | 播放按钮 `disabled`；选集按钮仍可用（换集不需要时长） |

`fsShownPos = scrubbing ? fsScrubPos : playPos` 是这两条链路的唯一分叉点：拖动中显示值
冻结在手指位置，其余时间永远等于真实播放位置。

| 检查项 | 结果 |

| 底部条 | `1920×72 @ y=1008–1080` |

## 6. 红线

1. **`.fs-bar` 高度恒为 `--pf-fs-bar`**。视频扣减、mpv 矩形扣减都读这个值，
   条一变高就有 72px 的画面被盖住。窄屏只许减内容，不许换行/加高。
2. **轨道与按钮必须在同一个 flex 行**。改成绝对定位或第二行，中线就得靠手调，
   字号或文案一变就错位。
3. **全局 `button { min-height: 34px }`**：任何低于 34px 的自定义按钮都要写
   `min-height: 0`。
4. **拖动期间不许 seek**。`onTrackMove` 只更新游标与气泡，`onTrackUp` 才 `commitSeek`；
   否则每帧一次 `mpv.seek` 会把内核拖死。
