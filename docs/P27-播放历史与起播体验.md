# P27 播放历史记录缺失 & 起播加载体验

> 两个用户可感知的问题一起修：
> ①「播放历史记录不上（或记了但不对）」
> ②「一直停在正在启播…，不知道在等什么，也退不出来」
>
> 结论先说：历史丢记录的主因是**渲染层把 Vue 的 reactive Proxy 直接扔进 Electron IPC**，
> 结构化克隆当场抛错，而这次调用是 fire-and-forget —— 失败完全无声；
> 次因是**打点事件挂在 `sourceTaskId` 的「值变化」上**，而内核按 URL 复用任务，
> 同一集重播时 id 不变，事件根本不触发。

---

## 1. 现象与复现

| 现象 | 复现步骤 |
|---|---|
| 历史页一直是空的 | 首页/发现页点任意卡片起播（成功播放、有声音有画面）→ 进「播放历史」→ 空态 |
| 重播不置顶 | 播过的片再播一次 → 历史里那条时间不变、也不排到最前 |
| 偶发「记录串片」 | 后台预取任务产生源健康度事件时，记录可能挂到用户没播过的条目上 |
| 起播转圈无反馈 | 源站慢/挂掉时，卡片只有一个小转圈，最长可转 30~60s，无法取消 |

---

## 2. 根因

### 2.1 主因：reactive Proxy 过不了 IPC（历史整体丢失）

`stores/history.ts::record()` 把 `catalog.playCtx.groups` 原样塞进 RPC 参数。
`playCtx` 是 Pinia state，读出来的 `groups` 是 **Vue 的 reactive Proxy**，
而 `preload` 是 `ipcRenderer.invoke('pf:rpc', { method, params })` —— 参数要走结构化克隆。

在真实 Electron 里实测（`.histcheck/ipc/`，与项目 preload 同构）：

```
proxyError: "An object could not be cloned."
plainOk:    true
```

只要播放的是「聚合/详情/分类」里的片（`groups` 非空，也就是绝大多数入口），
这次 RPC 必然 reject；`record()` 的 `catch` 只把消息写进 `state.error`，
UI 上没有任何提示，**历史一条都写不进去**。
（同一个坑本仓库早有前科：`catalog.addFavorite()` 里就写了「Vue reactive Proxy 不能过 Electron 结构化克隆」。）

### 2.2 次因：打点信号选错了（重播不记录 / 不置顶）

```ts
// 修复前
watch(() => store.sourceTaskId, (id) => { ...history.record(...) })
```

内核 `create_task` 里有一条 `find_task_id_by_url` —— **同一 URL 复用同一个任务 id**。
于是「同一集再播一次」时 `playTask()` 设置的是同一个 id，`watch` 不触发：

- 历史里那条记录的 `played_at` 不刷新 → 不置顶、时间还是上次的；
- 进度也不会重新归位。

用真实 UI 复现过：点两次同一张卡片，任务列表里始终只有 `task-1`，修复前第二次打点次数 = 1。

### 2.3 打点一次失败就永久丢

`record()` 只有一次机会，内核重启/繁忙时这条记录就没了；
进度上报依赖 `activeKey`，`activeKey` 又是 record 成功后才赋值的 —— 打点失败的窗口期内播的时长全部丢弃。

### 2.4 记录会被后台任务「劫持」

```ts
// 修复前 handleEvent / SourcesUpdated
if (!this.sourceTaskId || this.sourceTaskId === p.taskId) {
  this.sourceTaskId = p.taskId   // 为空时认领任意任务
  ...
}
```

任何后台任务（预取/巡检）的源健康度事件都能把空的 `sourceTaskId` 抢走，
后续打点就会带着「用户没播过的任务 + 上一部片的上下文」，形成串片记录。

### 2.5 起播没有任何上限

`playCard()` 逐个试站，`fetchDetail` / `task.create` 都没有超时：
内核 `fetch_text` 单次能挂 30s 以上，4 个站串行 = UI 可以转两分钟。
`HomeView` 的 `playingKey` 只驱动一句「正在起播…」，既没有阶段，也没有取消出口。

另外顺手发现：`HomeView` 的 `playingKey = card.key`，而卡片渲染用的是 `'r-' + card.key` ——
**真实影片的封面加载层其实从来没显示过**（只有轮播按钮能对上）。

## 3. 改动

### 3.1 渲染层 RPC 统一纯化（治本，覆盖所有同类调用）

`stores/player.ts`

```ts
export function toPlainParams(params: unknown): unknown {
  if (params === undefined || params === null) return params
  try { return JSON.parse(JSON.stringify(params)) } catch { return params }
}
// rpc(): api.rpc(method, toPlainParams(params)).catch(...) → 顺带剥掉 "Error invoking remote method" 外壳
```

所有 store 的 `rpc()` 都走 `player.rpc()`，一处收口，历史记录不再是唯一的受害者。
`history.record()` 里另外对 `groups` 再做一次纯化（双保险，也方便单测断言）。

### 3.2 打点改成「起播事件」，不再监听 task id

`stores/player.ts` 新增：

```ts
playSeq: 0,
lastPlay: null as null | { taskId: string; url: string; title: string; at: number },

markPlayStart(t: Task) {        // playTask / createTask 两个真正的起播汇合点调用
  this.playSeq += 1
  this.lastPlay = { taskId: t.id, url: t.url, title: t.title ?? '', at: Date.now() }
}
```

`PlayerView.vue` 的两个 watcher 合并成一个 `watch(() => store.playSeq, ...)`，顺序固定：
先补「散片上下文」（媒体库/网盘/解析入口），再 `history.record(...)`。
即使内核复用同一个任务 id，`playSeq` 也会自增 → 每次都打点、每次都刷新 `played_at`。

### 3.3 打点失败进队列，恢复后按序补写

`stores/history.ts`：

- `pendingQueue: HistoryRecordPayload[]`（同片同集去重、上限 10 条）；
- `writeOnce(payload, replay)`：一次真实写入，失败返回 `false` 交给调用方入队；
- `drainQueue()`：串行重放，中途失败立刻停下留待下次（`draining` 防重入）；
- 补写成功时，只有「正好是当前在播那条」（`payload.episodeUrl === lastPlay.url`）才接管
  `activeKey` 与进度补写，旧记录不会抢走进度归属；
- `pendingProgress`：`activeKey` 尚未落地时的进度先缓存，落地后立即补写。

`PlayerView` 在内核 `online` 翻转时调一次 `history.flushPending()`。

### 3.4 源健康度事件不再改写 `sourceTaskId`

只有 `sourceTaskId === 事件 taskId` 时才更新 `sources`；`sourceTaskId` 只由起播/删除显式改写。

### 3.5 起播体验：分阶段 + 硬超时 + 可取消 + 可重试

`stores/catalog.ts`：

```ts
const BOOT_DETAIL_MS = 9_000     // 单个片源拉详情上限
const BOOT_TASK_MS   = 12_000    // 建任务 + 起播上限
const BOOT_BUDGET_MS = 26_000    // 一次点击的总预算

boot: { key, title, phase: 'detail'|'task'|'start', attempt, attempts, startedAt } | null
```

- 每个片源：`withTimeout(fetchDetail, 9s)` → 超时就换下一个站，并把原因记进 `reasons`；
- 总预算 26s：剩余时间不足就带着「已尝试 N 个片源 + 每个的具体原因」报错；
- `cancelBoot()`：翻 `bootSeq` 让循环退出，**同时翻 `playSeq` 作废在飞的 `task.create`**
  （否则十几秒后任务建好，页面会「先报错、再突然跳进播放页」）；
- `playEpisode()` 内部也给 `task.create` 加了超时，并修掉一个旧 bug：
  过期分支只删除「本次新建」的任务，**复用的既有任务不再被误删**
  （曾经两次快速点同一集会删掉正在播的那条，表现为点了变黑）。

UI（`HomeView.vue`）：

| 时间点 | 界面 |
|---|---|
| 0-3s | 封面遮罩：转圈 +「正在获取片源（1/2）…」+ 计时 |
| ≥6s | 追加一行「源站响应较慢，稍后会自动换下一个片源」 |
| ≥3s（创建任务） | 文案切「正在创建播放任务…」 |
| 全程 | 遮罩右下角「取消」按钮（`pointer-events` 单独放开） |
| 失败 | 列表上方红框提示条：完整原因 + 「重试」+「知道了」，toast 只留一句话 |

`DiscoverView.vue` 同样补了阶段文案 + 取消（海报角标 + 播放按钮）。
`HistoryView.vue`：续播加 20s 上限、首屏骨架、错误可关闭、「已看完」徽章 +「重看」按钮。

### 3.6 播放页：起播看门狗

`PlayerView.vue`：`playing` 转真后再挂 15s 看门狗，hls 内核到点仍 `readyState < 2` 就把
「正在缓冲…」升级成「15 秒内没有拿到可播放的分片，这条线路可能已失效」+「重新加载」按钮。
连播结束（`ended`）时先 `flushProgress()`，片尾进度不再少最后几秒，「已看完」判定才准。

## 5. 已知取舍

1. **同集重播保留旧进度**（内核 `same_episode` 分支）。历史里点「重看」时侧栏从 0 开始，
   但库里那条仍显示上次进度，等 5s 节流上报后才归零。改它要动 Rust 契约（加 restart 参数），
   本次没做。
2. 队列上限 10 条：离线期间播超过 10 部，最早的记录会被丢弃（避免长时间离线堆内存）。
3. 起播预算 26s 是「体验优先」的选择：极慢但可用的源会被判超时。真要救这类源，
   应该在侧栏手动换线路，而不是让用户对着转圈等。
