# P36 · 起播静默失败加固（“视频播放不出来”排查）

> 触发：用户反馈「现在视频播放不出来了」——现象为黑屏、没有画面、一直转圈，
> 场景是首页/发现点卡片起播，内核不确定。

## 1. 排查矩阵（结论：主链路本身没坏）

排查方式：拉起**真实应用**（真实 main + preload + pf-core），用 CDP 接管，
直接驱动 Pinia store 与 UI，采样 `video.readyState / videoWidth / currentTime`
与 `mpv.time-pos`。脚本为一次性 `.probe/*.mjs`（不留在仓库）。

| 用例 | 片源 | 结果 |
|---|---|---|
| 内核链路（`node smoke-p21.mjs`） | 本地假片源 | 12 通过 / 0 失败 |
| hls.js 直链起播 | 用户库里《家乡美食大赛》 | 1.5s 出画，1280×720，`ct` 推进 |
| hls.js 解析页起播 | 用户库里《吞噬星空 241 集》`vv.jisuzyv.com/play/…` | 3s 出画，1920×1080 |
| libmpv 起播 | 同上 | `video-params` = d3d11/nv12 1280×720，`time-pos` 推进 |
| 首页点卡片 | 真实 CMS 首卡 | 3s 出画，1920×1080 |
| 发现页点卡片 | 真实 CMS 首卡 | 命中缓存，1.5s 出画 |
| 亮色皮肤 | 同上 | 正常出画 |
| 820×620 窄窗口 | 同上 | 视频区 684×385，正常出画 |
| 类型检查 | — | `pnpm -r typecheck` 全绿 |

布局预算也复测过：`--pf-card-chrome=176`、`--pf-card-room=144`、
视频区 1225×689（视口 1920×1009），未发生裁切。

也就是说 **P28/P30/P34 没有破坏播放链路**。真正的问题在“失败时什么都不说”。

## 2. 找到的三个缺陷

### 2.1 起播靠 `tasks.find(url === u)` 反查 → 失配即静默

`task.create` 的 RPC 返回值本来就带任务快照（`ok_response(json!({ "task": task }))`，
注释明确写着“成功返回含 playUrl 的任务快照”），但 renderer 把返回值**丢了**，
改用 `this.tasks.find((x) => x.url === u)` 反查。

- 内核侧只要对 URL 做过规范化（补协议、去尾斜杠、大小写），严格相等就失配；
- `find` 返回 `undefined` → `if (t?.playUrl)` 整块跳过 → **不起播、不报错**；
- 页面停在黑底占位，用户看到的就是「点了播放没反应」。

修复：优先用 `res.task`，`find` 降级为兜底；拿不到任务或 `playUrl` 时报出可读原因。

### 2.2 非 HLS 分支把任意 URL 丢给 `<video>` 并直接宣告“在播”

```ts
if (!isHlsSrc) {
  video.src = src
  void video.play().catch(() => {})   // 失败被吞
  this.playing = true                 // 却已声明在播
}
```

解析页、网盘分享页这类网页 URL 走到这里，浏览器必然失败，但结果是
`playing=true` + 无画面 + 无提示，连 `.stall-hint` 都不会出现
（`checkNoPicture` 在 `playing` 为假时才不跑，为真才跑；而 `readyState` 永远拿不到）。

修复：新增 `looksLikeDirectMedia()` 前置校验（放行 `blob:` / `data:` / `/file` /
带媒体扩展名的路径，判不准时放行，避免误伤带签名的直链）；`play()` 的 reject 不再静默。

### 2.3 日志被 `→ downloading` 刷屏

`precache` 全量下载时，内核每个分片都推一次 `TaskUpdated`，
renderer 无条件 `pushLog` —— 100 条日志槽每秒被同名状态顶满：

```
info: 任务更新：task-…703-0 → downloading
info: 任务更新：task-…426-0 → downloading
info: 任务更新：task-…703-0 → downloading
```

真正的「解析完成 / 站点提取成功 / 命中缓存 N/M」全被挤掉。
排查时打开调试面板什么也看不到，这也是本次定位变慢的直接原因。

修复：只有 `status` 真的变化才记一行。

## 3. 验证

改后重建（`pnpm --filter @polyframe/desktop build`），同一套 CDP 用例回归：

- 直链起播：1.5s 出画 1280×720
- 卡片起播：1.5s 出画 1920×1080（命中缓存）
- 日志：`经代理播放 / 解析完成 / 命中既有缓存 / 站点提取成功` 全部可见，无重复刷屏
- `typecheck` 全绿，renderer 无 console 报错

## 4. 仍需现场确认

本次无法复现用户的“完全不出画”，下列情况需要下一次现场的调试面板日志才能定性：

- 源站 WAF/限速导致分片长时间 403（此时应看到 15s 后转成
  「15 秒内没有拿到可播放的分片，这条线路可能已失效」+ 重新加载按钮）；
- 库里有 3 个 `precache` 任务长期停在 `downloading`（`家乡美食大赛` 与
  `吞噬星空 240/241 集`）。`precache` 语义是全量预缓存，长片会持续占用
  worker 与带宽；若用户网络较窄，起播首片要排在这些任务后面。
  这一条是否要改成“播放优先、预缓存让路”，待确认。

## 5. 排查方法留档

```bash
# 真实应用 + CDP 接管（不依赖打包、不改 main）
node .probe/probe-play.mjs            # 逐页采样 + 截图
node .probe/probe3.mjs <直链>          # 指定片源起播
node .probe/probe4.mjs --engine mpv --theme light --size 820x620
```

要点：
- `spawn(electron, ['apps/desktop', '--remote-debugging-port=9333'])`，
  用 `puppeteer-core` 的 `connect({ browserURL })` 接管；
- store 从 `document.querySelector('#app').__vue_app__.config.globalProperties.$pinia` 取；
- libmpv 的画面是 Win32 子窗口，`capturePage` 截不到，必须用 RPC
  `mpv.get {name:'video-params'}` + `mpv.time-pos` 判断；
- 强制结束 Electron 不会留孤儿 `pf-core`（已验证 `tasklist` 干净）。
