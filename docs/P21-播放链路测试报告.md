# P21 播放链路测试报告（链接有效性与播放能力）

- 测试日期：2026-10-30
- 被测对象：`pf-core.exe`（release，`apps/core/target/release/pf-core.exe`）+ 桌面端起播链路（`stores/catalog.ts` → `task.create` → 代理 → 播放器）
- 触发背景：用户在桌面端点击某集时报
  `create task failed: HTTP 403 Forbidden https://super.ffzy-online6.com/.../index.m3u8；页面未发现 m3u8/mpd/mp4 流。将 yt-dlp.exe 放入应用目录或 PATH 可解锁站点提取`，
  并反馈「随意点击几个视频即无法播放」。

## 1. 结论摘要

| 结论 | 证据 |
|---|---|
| 全链路（清单→分片→密钥→mpv 入口）**47 例中 45 例可播放**（95.7%）；同类两轮分别为 45/48、45/47，失败全部落在外部因素 | 第 4/5 节 |
| 用户报的 403 报错**存在两个缺陷**：① 403 是 CDN WAF 的软失败，重试 4 次仍失败才报错，本身不一定是应用 bug；② 失败后仍去扫页面，把「源站拒绝直链」错误归因为「页面里没有流」，并给出「装 yt-dlp」的无效建议 | 第 6 节 F1 |
| 「随意点几个就播不了」**复现成功**：16 路并发 `task.create` 时单请求 8s 超时→重试，创建延迟全部顶到 **18.8s**，且 **1/16 直接超时失败** | 第 6 节 F3 |
| mpv 内核的 `/master.m3u8` **单次回源，抖动即 502 → 黑屏**（首轮 C-2 复现） | 第 6 节 F4 |
| 4 处缺陷已修并回归：`smoke-p21` **12/12**、单元测试 **38/38**、全量审计 **45/47**、极端连点 **14/16 → 15/16（无超时类失败）** | 第 7 节 |
| 剩余 2 例失败均为**非应用缺陷**：1 例本机代理导致 mux 分片不可达，1 例慢分片 20s 未返回 | 第 6 节 F6 |

**覆盖的播放层级**（任一层失败即判该例失败）

1. **清单层**：`playUrl` 200 且含 `#EXTM3U`、`#EXTINF` 非全 0、分片数 > 0
2. **分片层**：随机 3 个分片真实 GET，要求 200/206、字节数 > 256、内容嗅探为 TS(`0x47`) 或 fMP4(`ftyp/moof`)；返回 HTML/JSON 判为被拦截
3. **密钥层**：`EXT-X-KEY(METHOD≠NONE)` 时密钥必须可取
4. **mpv 入口层**：`masterUrl` 必须非 5xx 且可解析（桌面端 mpv 内核唯一入口）
5. **时效层**：连点组在 +5s 后再验一次，捕捉「创建时能取、真播时已失效」

**不在本次范围**：网盘源（P9b）、磁力（P12）、弹幕（P14）、字幕与音轨切换、DRM（Widevine/FairPlay）、直播流。

## 6. 失败场景：现象 / 复现步骤 / 定位结论

### F1【用户报障】403 被误判成「网页里没有流」

**现象**
`create task failed: HTTP 403 Forbidden https://super.ffzy-online6.com/20261021/43765_7d312756/index.m3u8；页面未发现 m3u8/mpd/mp4 流。将 yt-dlp.exe 放入应用目录或 PATH 可解锁站点提取`

**复现步骤**
1. 任一 CMS 源里点开一部片 → 点某一集（URL 形如 `.../index.m3u8`）
2. 该 CDN 此刻对直连返回 403（WAF/防盗链风控）

**定位过程**
- 该 URL 现在直连/走代理均返回 200（`#EXTM3U` master → 703 分片），且 `curl` 并发 25 次全 200 → **不是稳定封禁，是间歇性风控**
- `pf_parser::fetch_text` 已把 403 归为软失败并重试 4 次（0.5/1.5/3s 退避、每次换新 client 以换边缘节点）
- 但 `probe_and_start_inner` 在 `load()` 失败后**无条件**走 `extract_fallback`：把一个 `.m3u8` 当网页去扫 → 必然「未发现流」→ 错误信息被替换成与事实无关的「页面/yt-dlp」结论

**结论**：403 本身是外部风控（重试后仍 403 才失败，属可接受）；**应用缺陷是错误归因与无效建议**。

**修复**
- `pf-parser` 新增 `looks_like_media_url()`（扩展名 + `/hls/` + `m3u8` 形态）
- `pf-engine` 在直链媒体解析失败时**跳过页面提取**，直接返回带处置建议的错误：403 → 「防盗链/风控，多为临时性，换源或稍后重试」，404/410 → 「源站已无此文件，多为采集站滞后，换源重试」，5xx → 「边缘节点故障」
- 效果：404（确定性失败、不重试）**约 1~2s** 给出结论；403（软失败，走完 4 次重试）约 5~8s 给出结论。两者都不再额外白扫页面，也不会再出现「页面未发现 m3u8 / 装 yt-dlp」的误导信息。

### F2【源站数据滞后】当天新集 404

**现象**：`HTTP 404 Not Found https://super.ffzy-online6.com/20261030/44499_5cdc523d/index.m3u8`

**复现步骤**：任意 CMS 源 → 选一部「今日更新」的剧 → 点最新一集。

**定位**：`20261030/` 目录下的新集全部 404，同一部剧的往期集数与其它源同剧集均正常；直接 curl 该 URL 也是 404。采集站已收录、CDN 尚未铺文件，**应用侧无法修复**。该现象在多轮运行中反复出现（第 2/3 轮各命中 2 例，终版抽样未命中），是「点了没反应/播放失败」在真实使用中最常见的一类。

**结论**：非应用缺陷。修复后用户看到的是「源站已无此文件：多为采集站数据滞后，换源重试」，而不是含糊的「页面未发现流」。

### F3【核心复现】连点导致创建超时

**现象**：连续快速点多个视频时，其中一条 `task.create` 直接失败（`The operation was aborted due to timeout`），其余延迟从 2~4s 恶化到 **18.8s**（几乎完全一致，是「8s 单次超时 + 退避 + 重试」的特征）。

**复现步骤**（`storm-bench.mjs`）
1. `node storm-bench.mjs --n 16 --gap 0`（16 条不同集数，同时发出，等价于用户狂点）
2. 观察每条 create 的耗时与最终可播状态

**修复前**：成功 14/16，p50 = 18775ms，max = 18779ms，1 条超时失败。

**定位结论**
- 无并发时 p50 仅 3.2s；16 并发时每个 create 都要拉 master + variant 两跳 playlist，8 条以上就会把同一 CDN 的连接打满，单请求撞 8s 超时，重试把总延迟抬到 ~19s，最坏 4 次全超时 → 失败
- 每个成功创建的任务都会立刻启动 4 路分片预取；用户实际只想看最后一个，剩下十几个任务在后台持续吃带宽，进一步恶化后续点击
- 前端 `playEpisode` 对用户连点没有任何收敛：点 16 次就发 16 次 `task.create`

**修复**
1. `pf-parser::fetch_text` 加进程级并发闸门（8 路）——这些请求都很小，限流不拖慢单次，只避免自我拥堵
2. 前端 `catalog.playEpisode` 引入 `playSeq`：**只有最后一次点击有效**；返回时若序号已过期，直接 `task.delete` 掉刚建的任务，不再堆积后台预取
3. 修后极端 16 连点：**15/16，且不再出现超时类失败**（唯一失败仍是 F2 的 404）

### F4【mpv 黑屏】`/master.m3u8` 单次回源即 502

**现象**：首轮审计 C 组 +5s 复验时 `masterUrl HTTP 502（mpv 内核无法起播）`。桌面端 mpv 模式下画面来自这个入口，502 等同于黑屏，但播放器不会报错。

**根因**：`master_playlist()` 每次播放都用**一次**上游请求重新拉 master（不重试、不用已解析的 IR），边缘节点一次抖动就 502。

**修复**：3 次短退避重试（300/600ms）；仍失败则**退回本地已解析的 media playlist**——丢掉清晰度选择，但保证有画面。`smoke-p21.mjs` 用「建完任务就把源站关掉」验证：修复前 502，修复后 200 + `#EXTM3U`。

### F5【外部】CMS 详情 503

`《请你们原地结婚》详情 HTTP 503`，源站自身故障，`fetch_text` 已重试 4 次仍 503。非应用缺陷，下一次点开或换源即恢复。

### F6【环境】mux 分片超时

`test-streams.mux.dev` 的分片在本机**走代理 13.7s 超时（000）、直连 200/7.1s**。即失败由本机 127.0.0.1:3918 代理造成，非应用缺陷。真实用户无该代理时应可播放，但 7s/分片也说明该源本身很慢。

同类还有终版 C 组唯一失败：`vip.dytt-tvs.com` 的 553 分片源，清单 200（2.5s 取回）但随机抽样分片 20s 未返回。这类「清单正常、单分片极慢」在播放器里的表现是**卡住而不是报错**，属于源站带宽问题；内核侧只能靠多源择优规避。

### F7【测试器自身缺陷】大清单被误判为非法（已修）

首轮 4 例「清单非 m3u8（前 60 字节为空）」是**审计脚本的 bug**：为省内存，>200KB 的响应体不保留文本，导致 4469 分片、365KB 的合法清单被判失败。改为整份判断后全部通过（该源 4469 分片 / 8984s，播放正常）。

## 9. 遗留风险与建议

1. **源站数据滞后无法根治**：采集站先收录、CDN 后铺文件（尤其当天更新的集）。建议在播放页错误提示里直接给「换源」按钮（详情弹层已有换源 chips，可复用），而不是让用户自己去切。
2. **CDN WAF 间歇 403 无法根治**：当前策略是 4 次重试 + 新 TLS 会话，命中间歇性风控时会在 5~37s 后失败。若要进一步降低，需要引入系统级 HTTP 代理/多出口或指纹伪装，成本较高。
3. **连点仍有秒级等待**：即使收敛为「只有最后一次点击生效」，那一次仍要等源站返回（单点 p90 6.8s）。极端 16 路同发时（自动化压测，真人点不了这么快）延迟仍在 **18~20s**，这是 16 条 playlist 抢同一 CDN 的物理上限，闸门只能消除失败、不能消除排队。如果用户可感知「点了没反应」，建议在卡片/弹层上加「正在解析…」的即时反馈（当前只有按钮 disabled）。
4. **mpv 入口仍依赖一次实时回源**：退回本地清单只是兜底，清晰度选择会丢失。彻底方案是在建任务时把 master 原文缓存到 IR，`/master.m3u8` 优先读缓存。
5. **慢分片**：部分 CDN 单片 2MB / 5~7s，播放会卡顿而非报错。若要量化，需要在真实播放器上看 `stalled` 事件，内核层测不出。
